## 开场：一句话讲清 DSpark 干了啥（对应 blog 第 0 节）

各位好，今天给大家讲一篇今年七月的论文，叫 DSpark，是 DeepSeek 团队发的，arXiv 号 2607.05147。论文全名是 DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation，作者 Xin Cheng 等 32 人，DeepSeek。最实在的一点是——【加重】**它已经部署进了 DeepSeek-V4 的生产环境，在真实用户流量下，每个用户的生成速度提了 60% 到 85%。**这个数字是硬的，不是实验室数字，所以值得讲。

那 DSpark 干了啥？一句话：**它治的是投机推理里两个一直被忽视的瓶颈。**

- 第一个叫**草稿后段衰减**。并行起草器一次出一整块草稿，但每个位置是"各猜各的、互相看不见"，越往后猜得越不准，接受率快速衰减。DSpark 用**半自回归**——就是并行骨干加一个极轻的串行头——来治它，接受长度涨 16% 到 18%。
- 第二个叫**高并发验证浪费**。生产环境一忙起来，"无脑全验"会把服务器的 batch 容量浪费在那些注定要被拒掉的 token 上，拖垮整台机器。DSpark 用**置信度调度验证**——只验值得验的——来治它。

【加重】**第二点，才是那 60% 到 85% 生产提速的真正来源。**第一点只是辅助。这两个组件各打一个杠杆，后面会展开。

## 第一部分：为什么需要 DSpark——两个被忽视的瓶颈（对应 blog 第 1 节）

先看论文 3 节 Architecture 开篇的一句话，我把原文意思念一下：

> 回顾公式 1，投机推理的单 token 延迟 L = (T_draft + T_verify)/τ。自回归起草器 τ 高，但起草成本 T_draft ∝ γ；并行起草器把 T_draft 压成一次前向，但因为每个位置独立预测，牺牲了 τ。同时，固定长度验证把 T_verify 浪费在"几乎注定被拒"的低置信后段 token 上。

这段把 DSpark 要治的两个病，钉死在一个公式上：

> **L = ( T_draft + T_verify ) / τ**

这个公式是读整篇论文的钥匙，我把它拆开讲。τ 是平均一次投机能接受几个 token。分母 τ 越大、分子越小，推理就越快。分子有两项：T_draft 是起草的时间，T_verify 是验证的时间。

那论文里点名的三类东西，我一个一个讲清楚——【加重】**这就是大家最容易跳过、但最该听明白的三件事：自回归起草器、并行起草器、固定长度验证。**

**第一类，自回归起草器，代表是 EAGLE 系列。**它是怎么起草的？一个位置一个位置往后猜，每个位置都看前一个采样的 token。好处是准，因为每步都条件在前面真采到的东西上，所以 τ 高。坏处是慢——起草成本 T_draft 跟块大小 γ 成正比，猜几个就要算几次。猜越多越慢，所以被迫用小的 γ、用浅架构，比如就一层。这是它的命门：想要长块、深架构来提精度，速度就付不起。

**第二类，并行起草器，代表是 dFlash。**它反过来，一次前向就把 γ 个草稿 token 全算出来，起草成本 T_draft 跟块大小 γ 解耦了——猜 4 个和猜 15 个，起草都只要一次前向。所以它可以用大块、深架构。**但代价是：每个位置独立预测，互相看不见。**位置 2 算的时候，不知道位置 1 实际采到了哪个 token。后果就是后段衰减，越往后接受率掉得越快。这个后面单独讲。

**第三类，固定长度验证。**注意这个不是起草器，是验证侧的毛病。什么叫固定长度？就是不管草稿可不可信、不管服务器忙不忙，验证的时候**无脑把整块草稿都拿去目标模型验一遍**。问题是：后段那些低置信的 token，本来几乎注定要被拒，你还花 T_verify 去验它们——**这就是把宝贵的验证算力，浪费在注定被拒的 token 上。**单个请求看浪费不多，但高并发下，每个请求都这么浪费，batch 容量就被这些废 token 占满了，别的用户进不来，整台服务器就拖垮了。

所以，把公式 L = (T_draft + T_verify)/τ 重新看一遍，提升推理速度就是三个杠杆：

1. **降 T_draft**——起草更快；
2. **提 τ**——起草更准；
3. **降有效 T_verify**——验证更聪明，别把算力浪费在注定被拒的 token 上。

【加重】**DSpark 的两个组件，各打一个杠杆。**组件一半自回归，提 τ（顺便因为保持并行骨干，所以也等于降 T_draft）；组件二置信度调度验证，降有效 T_verify。**这是读整篇论文的钥匙，后面所有设计都能挂回这三个杠杆。**

### 两个瓶颈的相互作用（对应 blog 第 1 节后半，论文 3.2 引言）

再补一段，论文 3.2 引言讲这两个瓶颈怎么相互作用的，原文意思：

> 这个性能瓶颈来自两个相互作用的因素。第一，数据侧，草稿接受率天然随领域变化……第二，系统侧，多验一个 token 的真实成本，严格取决于引擎负载。负载轻的时候，多验一个即使被拒也几乎没代价；但高并发部署下，每一次不必要的验证都占了目标模型的 batch 容量，那些容量本来可以服务别的活跃请求。

意思是，验证到底该验多少，沿**两条轴**变：

- **数据轴**：代码这种结构化文本猜得准、接受率高；开放式闲聊猜不准、接受率低。不同请求草稿可信度不一样。
- **系统轴**：服务器闲的时候，多验一个 token 几乎免费，哪怕被拒也没关系；【加重】**但忙的时候，多验一个 token 就等于抢了别的用户 batch 容量。**这就是生产上的痛点。

所以"验多验少"不能一刀切——得看草稿可信度，**加** 当前负载。这正是置信度调度验证要把这两个信号统一进一个调度决策的原因。缺一个都不行：只看置信度不看负载，忙的时候硬验照样拖垮；只看负载不看置信，不知哪个草稿值得验，乱丢乱留。**必须把质量和系统两个信号乘起来，才是完整决策。**

## 第二部分：起草器架构——自回归 vs 并行 vs dFlash（对应 blog 第 2 节）

讲 DSpark 之前，得先认识它站在谁的肩膀上——**dFlash**。论文 2.2 节把现有起草器分成两类，我对照讲。

**自回归起草器**：逐个生成草稿 token，起草成本随块大小线性增长，T_draft ∝ γ，所以被迫用小 γ 加浅架构。代表是 EAGLE 系列。

**并行起草器**：一次前向出全部 γ 个草稿 token，T_draft 几乎跟块大小无关，所以可以用大块加深架构。但每个位置独立预测、互相看不见，所以后段衰减。代表就是 **DFlash**，Chen 等 2026 年的工作，目前最强的并行起草器。DSpark 直接拿它当骨干。

### dFlash 的 KV injection（对应 blog 第 2 节中段）

dFlash 比 EAGLE 强在哪？强在一个叫 **KV injection** 的招。论文原话意思：dFlash 给草稿模型条件在目标模型抽出来的丰富上下文特征上——叫 KV injection。

思路是"目标模型最懂自己"。大模型做 prefill 的时候，它每层的隐藏状态里，其实已经隐含了好几个未来 token 的信息。dFlash 就把这些多层隐藏状态抽出来、投影一下、注入到起草器**每一层的 K 和 V** 里。具体两步：

- 第一步，把目标模型多层的隐藏状态拼起来、投影，得到上下文特征 H_ctx，这是公式 2；
- 第二步，把这个上下文特征，跟草稿 token 拼起来，作为起草器每层的 K 和 V，这是公式 3。

这个比 EAGLE 的"塞输入"强。EAGLE 是把目标特征塞在输入层，但信息会随着层往下稀释；dFlash 注入每层 K/V，信息就一直在、不稀释。代价很小，大概 42MB 对 70GB 的模型，可以忽略。

### dFlash 的命门：后段衰减（对应 blog 第 2 节末尾，fig2）

但 dFlash 有命门，就是前面说的后段衰减。

【翻到 fig2】大家看这张图。横轴是草稿块里的位置，从 1 到 γ；纵轴是每个位置的**条件接受率**，就是"给定前面都被接受了，这一位能被接受的概率"。

- 上面那条，是自回归的 Eagle3，接受率稳，甚至往后还往上走——因为它每个位置都条件在前面真采到的 token 上，越往后上下文越充分、越准；
- 下面那条，是并行起草器 DFlash，接受率越往后掉得越狠——**这就是 suffix decay，后段衰减。**

这张图就是 dFlash 命门的实证。**DSpark 的第一组件，就是来补这一刀的。**

## 第三部分：DSpark 总体架构（对应 blog 第 3 节）

现在讲 DSpark 整体。论文 3 节原话意思：DSpark 用两个互补的组件来解决前面的局限——

- **组件一，半自回归生成**，见 3.1 节。一个并行骨干承担草稿计算的大部分，让 T_draft 几乎跟 γ 无关；再加一个轻量串行块，在草稿 token 之间注入依赖，在极小额外延迟下提升 τ。
- **组件二，置信度调度验证**，见 3.2 节。一个置信度头估计每个位置的接受概率；一个硬件感知调度器用这些估计来剪掉低置信的后段 token，砍掉不必要的验证计算。

对照起来：

- 组件一半自回归 = dFlash 并行骨干 + 轻量串行头 → 治后段衰减、提 τ；
- 组件二置信度调度验证 = 置信度头 + 硬件感知调度器 → 治高并发验证浪费、降有效 T_verify。

两个组件谁也不和谁抢活——一个打草稿侧杠杆（提 τ）、一个打验证侧杠杆（降有效 T_verify）。

### 一个完整解码周期（对应 blog 第 3 节，fig1，核心图）

【翻到 fig1——全篇最重要的图】

这张图是全文最重要的一张图，我带大家把一个完整的解码周期走一遍，每个字母都讲清楚。

论文图注的意思是：给定 prompt ABC，目标模型出一个 anchor D；DSpark 用重型并行骨干加轻量串行头，生成草稿 EFGH 和置信度 c1 到 c4；硬件感知前缀调度器评估这些分数，保留 EFG、丢掉低置信的 H；目标模型并行验证，E 接受、F 接受、G 拒绝，补一个修正 token G\* 完成本轮。

我把它拆成步骤，慢读一遍：

- prompt 是 A B C 三个 token；
- **第①步**，目标模型跑一步，给出一个 **anchor D**。这个 anchor 是目标模型亲自给的，干净、确定，作为这轮草稿的起点；
- **第②步**，DSpark 起草：用重型并行骨干加轻量串行头，**一次**出四个草稿 token E F G H，同时每个位置出一个置信度 c1 到 c4；
- **第③步**，硬件感知调度器评估这些置信度，决定保留 E F G，把低置信的 H 丢掉；
- **第④步**，目标模型并行验证 E F G：E 接受、F 接受、G 拒绝；
- **第⑤步**，G 被拒，目标模型从自己的分布重新采样一个修正 token 叫 G\*；
- 这轮结束，接受到的真 token 是 E、F、加 G\*，一共三个；**G\* 变成下一轮的 anchor。**

所以 DSpark 一个周期，能稳定产出好几个真 token。【加重】**这张图里"保留 EFG、丢 H"那个决策，就是第二组件干的活，第五部分细讲。**后面第四、第五部分把组件一、组件二讲透。

## 第四部分：组件一，半自回归生成——治后段衰减（对应 blog 第 4 节）

### 病根：多模碰撞（对应 blog 第 4 节前段）

先讲病根。论文 3.1 节原话意思：

> 并行起草器一次前向出全部 γ 个草稿 logits，所以每个预测不能条件在块里别处采样的 token 上。当上下文允许多种合理续写，比如 "of course" 和 "no problem" 时，并行起草器可能产出 "of problem" 或 "no course" 这种不连贯的组合，因为每个位置是对所有可能的前驱做平均，而不是条件在"实际采到的那一个"上。所以接受率沿块快速衰减……我们因此采用半自回归结构，把草稿生成分成两阶段。

病根就是**多模碰撞**。并行起草器一次出整块，每个位置**看不见本块别处采样的 token**。后果用论文那个例子讲最清楚：

假设上下文允许两种续写，"of course" 和 "no problem"。并行起草器同时算位置 1 和位置 2：

- 位置 1：可能是 "of"，50%；也可能 "no"，50%；
- 位置 2：可能 "course"，50%（配 of）；也可能 "problem"，50%（配 no）。【停顿】但位置 2 **看不见位置 1 实际采到了哪个**。

各自独立采样，就可能采出 "of" + "problem"，或者 "no" + "course"——都是胡说。因为每个位置是对所有可能前驱做平均，没有条件在"实际采到的那一个"上。**这就是 suffix decay 的根源。**

### 药：并行骨干 + 极轻串行头，"大件 + 小补丁"（对应 blog 第 4 节中段）

那药是什么？论文原话意思：

> 它让计算最重的草稿骨干完全并行，只追加一个轻量串行输出头，来注入局部转移信息。这个设计保留了并行模型的起草速度，同时显著缓解后段衰减。

思路一句话——【加重】**别让位置间完全看不见，让后段能"看见"前段采了啥、微调偏好。但绝不能回到"一个一个慢算"，那就毁了并行骨干的速度。**

所以叫"半自回归"，两个部件：

- **大件**：并行骨干，就是 dFlash。一次前向算完全部位置的"基础偏好"，叫 base logit U_k。它保留并行速度，不退化成慢算。
- **小补丁**：一个 Markov 头，是串行的。它只拿前一个采样的 token，给当前位置加一点点偏置，叫 B_k。它串行，但极轻，延迟可忽略。

"半自回归"就这么来的——大头并行、小头串行。【加重】**串行那部分必须小到不拖累延迟**，也就是 T_sequential 远小于 T_parallel，否则就毁了并行骨干的速度优势。

### Markov 头怎么算（对应 blog 第 4 节，公式 4、5）

具体怎么算？论文公式 4、5，我念一下意思：

- 整块草稿的联合概率：P(X|x_0) = 连乘 p_k(x_k | x_0, x_<k)；
- 每个位置最终选词：p_k = softmax( U_k + B_k )；
- Markov 头：B(x_{k-1}, ·) = W_1[x_{k-1}] · W_2，这是个低秩分解，r=256。

解读：每个位置最终选词，等于 softmax( 大件基础偏好 U_k + 小补丁 B_k )。Markov 头只看**前一个 token**：

- W_1[前一个 token]：把前一个 token 查表，变成一个 256 维向量；
- 再乘 W_2：投回成词表维度 V 的 logit 偏置。

说人话：**模型学了一张"词→词搭配"的低秩表。**起草时查一下"前一个是 of"，就把 "course" 加分、"problem" 减分——就把 "of problem" 这种串台治掉了。

为什么低秩、r 只取 256，不是全 V×V？因为词表 V 通常五到十五万，全矩阵得几十亿参数，太大；低秩后每个词只存一个 256 维向量，存储和每步计算都可忽略。**这是它能"轻到不拖速度"的关键。**

### position-1 小修改（对应 blog 第 4 节中段）

论文还有个小修改：dFlash 原版是把 anchor 加上 γ 个 mask token 当输入，只预测 mask 位置。DSpark 改成——**把 anchor 本身当作第一个预测位置**，所以 γ 个输入 token（anchor 加 γ−1 个 mask）能产出 γ 个草稿 logits。

意思是：dFlash 原版 anchor 只当条件、不产出预测，白白占一个输入位。DSpark 让 anchor 那位**顺便也产出一个预测**——白捡一位预测，省一次计算，质量不变。

### 实证一：小补丁参数效率极高（对应 blog 第 4 节，fig3）

【翻到 fig3】看这张图，论文图注意思：固定提议长度，DSpark 随层数增加而提升；值得注意的是，**浅的 2 层 DSpark，胜过更深的 5 层 DFlash 基线**，凸显串行建模的参数效率。

解读：**2 层 DSpark > 5 层 DFlash**——加一个极轻的串行头，比堆并行骨干的层更划算。**这证明"大件+小补丁"的精度-参数权衡极好。**

### 实证二：延迟开销极小（对应 blog 第 4 节，fig4）

【翻到 fig4】这张图论文图注意思：左三图是 DSpark 跨不同块大小持续优于 DFlash；右图显示串行头在 serving 时引入的延迟开销极小。

解读两个点：

- **右图**证明串行头"轻到不拖速度"不是空话——延迟开销极小，是实测的；
- **左三图**证明块越大 DSpark 优势越大，γ=15 时比 γ=7 优势更显著。因为后段越长，dFlash 衰减越狠，DSpark 治得越值。

组件一小结：**大头并行保速度、小头串行治衰减，不退化成慢算。**接受长度涨 16% 到 18%。

## 第五部分：组件二，置信度调度验证——治高并发验证浪费（对应 blog 第 5 节）

【加重】**这部分是 DSpark 真正的杀手锏，60% 到 85% 提速主要来自这里。**我多花点时间，分几小块讲。

### 5.1 思想：只把算力路由给"正回报"的 token（对应 blog 第 5.1）

论文原话意思：要充分释放大草稿块的潜力，需要一个统一机制，**只把目标模型算力路由给"预期回报为正"的 token**。DSpark 靠两个部件耦合来实现：一个置信度头，预测前缀存活概率；一个硬件感知前缀调度器，根据当前系统负载动态决定最优验证长度。

核心一句话——**只把目标模型算力，路由给"预期回报为正"的 token。**靠两个部件：置信度头给质量信号，硬件感知调度器给系统信号。

为什么缺一不可？单独一个都不行：

- 只有置信度、不看负载 → 知道哪个可信，但不知"验得起验不起"，忙时硬验照样拖垮；
- 只有负载感知、不看置信 → 知道多忙，但不知"哪个草稿值得验"，乱丢乱留。

**置信度调度验证把质量和系统两个信号乘起来，才是完整决策。**这个我在第一部分讲过，这里再强调一遍，因为它贯穿整个第二组件。

### 5.2 置信度头：打"能活过验证"的分（对应 blog 第 5.2）

先说置信度头。论文原话意思：置信度头对每个草稿位置 k 输出一个标量 c_k，在 0 到 1 之间。关键，c_k 建模的是**条件概率**——给定块里前面所有 token 都被接受了，位置 k 这位的草稿 token 能活过目标验证的概率。公式 7 是 c_k = σ( w⊤[h_k ; W_1[x_{k-1}]] )，是个 sigmoid。

所以每个草稿位置出一个分 c_k，在 0 到 1 之间，意思是——【加重】**给定前面都被接受了，位置 k 这位能活过验证的条件概率。**注意是条件概率，因为后面调度器要把它连乘。

**怎么训，这是最漂亮的一点。**训练标签 c\*_k 用的是**理论接受率**，公式 8：

> c\*_k = 1 − ½ × ‖p^d_k − p^t_k‖_1

这个 ‖·‖_1 是两个分布的总变差距离 TV。p^d 是草稿分布，p^t 是目标分布。直觉——**草稿分布和目标分布越像，TV 越小，接受率越高。**

这直接连回投机推理的接受概率 min(1, p^t/p^d)——把所有 token 的接受期望加起来，正好等于 1 减二分之一 TV。**所以置信度头学的本质，就是"这一位置草稿和目标差多远"**，把打分从拍脑袋变成有理论根据的。

### 5.3 STS 校准：让分的绝对值准（对应 blog 第 5.3）

这一步最绕，但关键，我慢慢讲。论文原话意思：

> 我们的硬件感知调度方法，恰好需要累积接受概率的**绝对量级**来算期望接受长度 τ。因为神经置信度估计常常过度自信……我们引入顺序温度缩放 STS……温度缩放是保序变换：它把预测概率校正到匹配经验接受率，但不破坏草稿 token 的相对排名。

为什么需要校准？因为调度器要用这些分算 τ，而 τ 是置信度的**连乘累加**——大概 τ ≈ c_1 + c_1·c_2 + c_1·c_2·c_3 + ……这样加。**连乘，需要绝对量级准。**但神经网络打分天生过度自信。连乘会把过度自信放大成灾难。给大家个数感受：

- 假设四个位置，真实存活率 0.7、0.6、0.5、0.4；
- 模型过度自信，输出 0.9、0.85、0.8、0.75，每个偏高一点；
- 四个全活的联合概率：真实 0.7×0.6×0.5×0.4 = 0.084；预测 0.9×0.85×0.8×0.75 = 0.459——【加重】**差 5.5 倍！**

每个位置单独看只偏高一点，连乘起来误差滚雪球。调度器拿错的 τ 决定"验多长"，会严重高估、过度验证、白占 batch。

**STS 怎么治：** 温度缩放就是给 logit 除个温度 T，降温、去自信。STS 特别在**逐位置、从左到右校准累积乘**：

- 位置 1，找温度 T1，让校准后 c1 ≈ 真实 0.7；
- 位置 2，c1 已定，找 T2，让 c1·c2 ≈ 0.42（前两位都活的真实率）；
- 位置 3，找 T3，让 c1·c2·c3 ≈ 0.21；
- 这样一位一位校准下去。

**关键：温度缩放是保序的**——只改绝对数值，比如把 0.9 压到 0.7；但不改排名，谁高谁低不变，不打乱"哪个 token 更可信"的判断。

【翻到 fig6】这是可靠性图，论文图注意思：Alpaca 上的可靠性图，原始置信度估计判别力强但过度自信；事后校准让前缀存活概率与经验接受率对齐。阴影直方图是各置信度 bin 的样本数分布。

解读：左图校准前，预测分全挤在高置信区，跟实际命中率对不上；右图 STS 之后，分和经验接受率对齐了。**这就是"绝对值变准、排名不变"的视觉证据。**

### 5.4 硬件感知调度器：贪心 + 早停（对应 blog 第 5.4）

现在两个信号都有了，怎么用？论文把验证长度选择形式化成一个全局吞吐最大化问题。我把几个关键量念一下：

- 这批总 batch size 是 B = Σ(1 + ℓ_r)，ℓ_r 是请求 r 验证的草稿长度；
- 期望被接受的总 token 数 τ = Σ(1 + Σ a_{r,j})，a_{r,j} 是请求 r 第 j 位的存活概率；
- 令 SPS(B) 表示引擎在 batch 等于 B 时的吞吐，单位步每秒。**关键，这条容量曲线是引擎初始化时 profile 一次、存成轻量代价表的。**
- 调度器要最大化 Θ = τ · SPS(B)。

核心就一个公式：

> **Θ = τ × SPS(B)**

- τ = 这批请求期望被接受的总 token 数；
- SPS(B) = 引擎在 batch=B 时每秒几步，B 越大越慢，是提前 profile 好的表；
- Θ = 每秒产出多少真 token，**要最大化。**

矛盾在哪？多验草稿，τ 涨，但 batch B 大了、SPS 跌。一增一减，Θ 先涨后跌，**找峰值。**

【加重】**"Hardware-Aware"——硬件感知——感知的就是 SPS 这条曲线。**它是引擎"batch 多大、每秒几步"的实测表。注意是**实测**的，不是理论算、不是统计估的：引擎启动时，拿不同 batch size 各跑几步、掐表测每秒几步，存成查找表。它把硬件所有真实行为压缩成一个实测值，换 GPU、换模型，重新 profile 一次照样能用。**这就是"硬件感知"四个字的全部含义。**

### 算法 1：贪心 + 早停（对应 blog 第 5.4 算法部分）

具体算法叫**贪心 + 早停**。论文原话意思：

> 因为 a_{r,j} 对 j 单调非增……把请求 r 的验证长度从 j−1 扩到 j，期望接受 token 的边际增益正好是 a_{r,j}……最优分配就是从全局池里贪心选存活概率最高的草稿 token……调度器用早停机制：当吞吐跌（Θ ≤ Θ_best）时立刻断开贪心搜索，截断决策只依赖到这一步为止的前缀。

因为"边际增益 = a_{r,j}（存活概率）单调递减"，所以把所有候选按存活概率从高到低排，贪心逐个纳入，每纳入一个算 Θ，**Θ 一跌就早停**。

我走个具体例子，三个请求 A B C，慢读：

- 候选按存活概率降序：(A,1)=0.8 最高，(B,1)=0.65，(A,2)=0.6，(C,1)=0.5……
- 基线啥都不验：batch=3，τ=3，Θ_best=3×SPS(3)；
- 纳入 (A,1)：batch 变 4，τ 变 3.8，Θ 涨，更新，继续；
- 纳入 (B,1)：batch 5，τ 4.45，继续；
- 纳入 (A,2)：batch 6，τ 5.05，继续，峰值附近；
- 纳入 (C,1)：batch 7，τ 5.55，微涨，更新；
- 再纳入 (A,3)：batch 8，τ 5.97，但 SPS 掉太多，Θ=406 小于峰值——**跌了！早停。**

最后返回：A 验 2 个、B 验 1 个、C 验 1 个，丢掉 A 的第 3、4 位那些低分 token。【加重】**不是所有请求验一样多——草稿可信的多验、不可信的少验、服务器一忙就少验。该验的验、不该验的丢。**这就是图 1 里"保留 EFG、丢 H"的算法实质。

### 实证：置信度阈值升，接受率升（对应 blog 第 5.4 末尾，fig5）

【翻到 fig5】论文图注意思：阈值 0 对应标准固定长度验证。阈值升，整体接受率稳步上升，因为置信度头有效剪掉了那些最终会被拒的 token，就是带阴影的那些条。

### 5.5 早停的一石二鸟：性能 + 无损，最妙的一点（对应 blog 第 5.5）

这部分是整个 DSpark 设计最精妙、也最容易被忽略的一点，我重点讲。论文原话意思：

> 无损投机推理严格要求非预期性：接纳决策不能依赖未来候选 token……回顾式全局搜索会把 x_{r,k} 泄漏进第 k 步的接纳决策，引入选择偏差……通过在吞吐跌时立刻断开贪心搜索，截断决策只依赖到这一步为止的前缀，这就把接纳事件跟未来 token 隔离开，保证严格恢复目标分布。

背景：DSpark 的置信度头用了 Markov 特征，依赖前一个**采样到**的 token。要算下一位存活概率，得先知道上一位采到了啥。那调度器能不能"先把整个块看完、回顾式地全局搜一个最优分配"？

**不能。**投机推理有个铁律，叫**非预期性**，non-anticipating——【加重】**接受或拒绝的决策，不能依赖未来的 token。**一旦"决定验不验第 k 位"时偷看了第 k+1 位，你就用未来信息挑了 token，引入选择偏差，**无损保证就破了。**

解法就是**早停**。Θ 一跌，立刻断，截断点**只用"到这一步为止"的信息**，不看后面——把决策事件和未来 token 隔离。

所以早停是**一石二鸟**：

- **性能上**：Θ 一跌就停，不浪费 batch 在低回报 token 上；
- **无损上**：截断只看前缀、不看未来，分布严格等于目标模型。

【加重】**这俩在系统设计里经常冲突**——要快就得近似、要无损就得严谨。置信度调度验证用一个算法结构，让它们一致了。**这是整个 DSpark 最该被记住的设计巧思。**

### 实证：负载自适应（对应 blog 第 5.5 末尾，fig8，最能体现组件二价值）

【翻到 fig8】论文图注意思：上排 a b 是不同并发水平下的聚合输出吞吐；下排 c d 是每请求平均目标验证预算。**并发负载上升时，动态调度器自动收紧每请求验证长度，防止资源争用。**

## 第六部分：训练——直接优化最终指标，不拐弯（对应 blog 第 6 节）

训练这块，论文 3.3 节。原话意思：训练目标三项——交叉熵损失 L_ce、分布匹配损失 L_tv、置信度损失 L_conf，三项都用位置权重 w_k = exp(−(k−1)/γ) 加权。L_ce 训草稿器猜对下一 token；L_tv 惩罚草稿和目标分布的总变差距离；因为总变差直接是接受率的代理——单步接受概率等于 1 − ½·‖p^d − p^t‖_1——所以最小化 L_tv 直接最大化期望接受率。L_conf 是二元交叉熵，训置信度头预测软接受标签 c\*_k。总目标是个加权组合，α_ce=0.1、α_tv=0.9、α_conf=1.0。

三项损失各训什么：

- **L_ce**，交叉熵，权重 0.1，训草稿器猜对下一 token——最朴素，权重反而最小；
- **L_tv**，分布匹配，权重 0.9，训草稿器分布贴近目标——【加重】**这是主损失**；
- **L_conf**，置信度，权重 1.0，训置信度头预测接受率，标签就是公式 8 的 c\*_k。

冻结：目标模型整体加草稿器的 embedding 和 LM head；只训骨干加串行头加置信度头。**参数效率高，草稿器像个轻量适配器。**

### 最值得讲：主损失是 L_tv，不是 L_ce（对应 blog 第 6 节中段）

这个权重分配**反直觉但极有道理**：交叉熵 L_ce 只给 0.1，分布匹配 L_tv 给 0.9。

为什么？因为投机推理要的不是"草稿偶尔猜对真值"，而是"草稿分布和目标分布贴近 → 被接受的概率高"。

- L_ce 只看"草稿在真值那一位对不对"——一个点；
- L_tv 看"整个分布贴不贴近目标"——整体形状。

而 **接受率 = 1 − ½·TV**，TV 就是分布差。所以【加重】**直接最小化 TV = 直接最大化接受率 = 直接优化"草稿会被接受"这件事本身。**L_ce 只是个防跑偏的辅助。

这是"目标对齐"的设计哲学：**训练损失直接对着推理时的真实指标（接受率）优化，而不是代理指标（猜对真值）。**和置信度头拿"理论接受率"当标签，是同一个哲学——不拐弯抹角，直接拿最终指标当监督。

### 位置权重为什么压早期（对应 blog 第 6 节末段）

w_k = exp(−(k−1)/γ)：第一位权重最大，等于 1，越往后越小。原因——**前缀式验证，第一个拒了后面全废**：早期位置错了，后面哪怕猜对也丢，所以早期准确性对 τ 贡献不成比例地大。三项损失共用这套权重，统一"优先保前段"，从 dFlash 沿用。

## 第八部分：总结与思考（对应 blog 第 8 节）

### 贡献收口

三句话：

1. 组件一半自回归（3.1）：dFlash 骨干 + Markov 头 → 治后段衰减，τ 涨 16% 到 18%；
2. 组件二置信度调度验证（3.2）：置信度头 + STS 校准 + 硬件感知调度器 → 治高并发验证浪费；
3. 训练（3.3）：主损失 L_tv 直接优化接受率，不用代理指标；
4. 实战：DeepSeek-V4 生产，60% 到 85% 提速，推动 Pareto 前沿。

### 六个值得记住的设计巧思

1. **"大件 + 小补丁"的半自回归**——大头并行保速度、小头串行治衰减，不退化成慢算；
2. **置信度头用理论接受率当标签**——从拍脑袋变成有理论根据，且直接连回接受公式；
3. **STS 校准连乘**——因为连乘放大偏差，必须逐位校准累积乘，不是全局一个温度；
4. **早停一石二鸟**——性能（省算力）加无损（不看未来），用算法结构让冲突的俩目标一致；
5. **训练直接优化最终指标**——L_tv 主损失直接最大化接受率，置信度标签也是接受率，目标对齐；
6. **硬件感知 = SPS 实测曲线**——把硬件行为压缩成一张表当代价函数，决策和生产对齐。

### 局限与诚实标注

也要讲局限，不能只说好的：

1. **很新**：dFlash 2026 年 2 月（ICML'26）、DSpark 2026 年 7 月（预印本加生产报告），独立第三方复现还没跟上；
2. **极端提速数字**是 DeepSeek 自家生产、在极端 SLA 下的数据，基线 MTP-1 接近运营边界，要打折看；
3. **SPS 简化假设**：只把 batch size 当主变量，真实非平滑特性要靠 5.2 节工程手段补；
4. **早停全局最优前提**：Θ 单峰才全局最优，隐含 SPS 平滑下降的假设；
5. **要训起草器**：不是即插即用、零成本。

### 判断

【加重】**DSpark 的真正价值，不在"+16% 到 18% 接受长度"，而在于把投机推理从"算法技巧"推向"系统级工程"**——它第一次让"投机预算"从静态变成按负载动态的量，并保证无损。**这是高并发 serving 场景下能用的投机推理，不是离线 benchmark 好看的投机推理。**

趋势：**并行骨干 + 轻量自回归修正 + 硬件感知调度**这条路，从 dFlash 到 DSpark，很可能成为下一阶段 serving 的主流，值得持续盯。
