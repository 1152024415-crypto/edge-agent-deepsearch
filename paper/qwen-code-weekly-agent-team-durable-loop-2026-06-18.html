研究背景与问题

这周 Qwen Code 周报。要解的痛点有三个：以前 /fork 起的后台 agent 各干各的，互相不通气，结果得自己手动拼；/loop 的定时任务一旦重启就静默消失，「每小时查一次 PR」这种长任务根本靠不住；想换工作目录得退出 CLI 重启，多仓来回切很不方便。这周就冲这三块做。

贡献点

发了 v0.18.0 到 v0.18.3 四个版本、100 多个 PR。一是 Agent Team 模式，模型能建命名团队、起多个并行队友、互发消息、共享任务列表、最后领队汇总一份报告，关键是队友是常驻的不是跑完就消失。二是 Durable /loop，定时任务落盘到 ~/.qwen/tmp 下按项目 hash 存，重启自动恢复，漏掉的周期任务补跑一轮，一次性提醒重启后先确认再执行。三是 /cd 命令，会话内切目录不重启，会话文件自动迁移、上下文自动刷新。

实现方法

Agent Team 默认关，开 experimental.agentTeam 或设环境变量后模型拿到建队、发消息、增删共享任务的工具，Agent 工具加 name 参数起常驻队友而不是一次性子 agent，队友干完一项等下一项。Durable /loop 判断请求是否要持久化，要的就写 scheduled_tasks.json，不在工作区里不进 git，重启时恢复；同项目多会话只一个 holder 跑，holder 崩了秒级另一个接手；周期任务 7 天自动过期。/cd 先校验目录和信任确认，更新 workspace 根和 cwd 服务，把当前会话的 transcript、runtime、worktree 文件迁到新会话目录，再刷系统目录上下文。

实验与结果

周报没跑 benchmark，只给工程指标：四个版本、100 多 PR；持久化任务写盘路径是 ~/.qwen/tmp/<project-hash>/scheduled_tasks.json；多会话 holder 崩溃秒级接管；周期任务 7 天过期。具体 agent 协作能提多少效率、恢复成功率、切换延迟都没量化。未报告具体数据。

对端侧 agent 的意义

这几块对端侧很有借鉴价值。Agent Team 的常驻队友加消息共享，端侧多 agent 协作同样需要：手机上几个小 agent 并行各管一摊还能互通，比一次性 fork 省资源。Durable /loop 把任务落盘按项目存、重启恢复、漏跑补一轮、多 holder 接管，这套持久化和容错思路端侧长任务直接能用，端侧更容易断电重启。/cd 会话内切目录加文件迁移，端侧 agent 跨工作区切换场景能参考。

局限与未来

没评测证明 team 模式真比独立 fork 快或更准，多 agent 通信开销没量化。持久化任务只到文件级，跨设备同步没提，端侧多设备场景缺这块。/cd 迁移会话文件，但跨会话或跨设备的会话迁移没做。Agent Team 是 experimental 默认关，稳定性没说。未来端侧落地要把落盘存储换成端侧安全存储、把多 holder 接管适配到边缘多节点，这周没给这些路径的基准。
