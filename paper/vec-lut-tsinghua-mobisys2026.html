Vec-LUT: Vector Table Lookup for Parallel Ultra-Low-Bit LLM Inference on Edge Devices

端侧推理超低比特量化查表加速LLM部署NPU

深度整理

研究背景与问题

端侧跑大模型已经被量化推到 4 比特、2 比特甚至 1.58 比特这种超低比特档位。配合查表（LUT）推理，CPU 跑这些超低比特模型甚至比专用 NPU 还快，让本地大模型看起来很有希望。但有一个被忽略的瓶颈：当需要并行推理时（比如 prefill 阶段一次处理多个 token、test-time scaling 同时生成多条候选、多 token 场景），LUT 推理吃不满内存带宽，速度上不去。根因在于传统 LUT 是标量范式，每个 token 都要重复做非连续内存访问，token 一多就把内存总线堵死。

贡献点

核心贡献是提出 Vec-LUT，一种面向并行 token 的向量查表范式。第一，把原来「每个 token 各自查一次表」改成「跨并行 token 构建一张统一 LUT，每个索引只做一次 1 到 N 的查表」，从根上消除重复访问。第二，配套两项实现技术：Vector LUT-Centric Tensor Layout 重新排张量布局让查表对齐，Cache-Aware Streamed Lookup 让访问顺序贴着缓存走、减少 miss。这两点合起来让超低比特 LLM 在并行场景下也能吃满带宽。

实现方法

输入是一批要并行处理的 token，流程大致是：先把这批 token 的索引聚合起来，构建一张覆盖整批的统一 LUT，然后对每个索引位置只做一次 1 到 N 的批量查表，一次性把多个 token 的结果取出来。关键在于张量布局按查表顺序重排，让连续访问落在连续缓存行上；查表过程被组织成流式，按缓存粒度推进，避免反复扫同一块内存。这样把原来 N 次 scalar 查表压成 1 次 vector 查表，访存次数和带宽利用都变好。

实验与结果

在 5 种端侧设备上、跨 3 个 LLM 做评测，对比当下最强基线，Vec-LUT 最高取得 4.2 倍加速。摘要没给具体设备型号、模型名、绝对延迟或能耗数字，只突出相对加速比。代码已开源（摘要里指向两个 URL）。整体属于工程性强、有实测、可复现的工作。

对端侧 agent 的意义

端侧 agent 跑起来要预填长上下文、要做 test-time 推理扩展、要多候选并行生成，这些都是多 token 并行场景。而当前超低比特 LUT 推理在单 token 生成上很快，一上并行就掉链子，正好卡住 agent 的咽喉。Vec-LUT 直接修的就是这条链路：让 agent 的 prefill 和多路采样不再被 LUT 访存拖累。对端侧 agent 工程师来说，这是把本地小模型从「能聊天」推进到「能跑 agent 工作流」的关键一环，而且代码开源可以直接接。

局限与未来

第一，4.2 倍是相对基线的峰值，摘要没给绝对吞吐和延迟，也看不出在不同 batch 大小下的稳定性。第二，只测了 5 种设备和 3 个模型，泛化到更多硬件（尤其手机 NPU、DSP）还不确定。第三，Vec-LUT 优化的是并行 prefill/采样，对单 token 自回归生成这种 scalar 场景帮助有限，得和别的 kernel 一起用。第四，作者没提精度损失——1.58 比特本身质量已经掉，叠加并行查表会不会再掉，需要看正文。未来值得把它和 agent 框架端到端联测，看实际 agent 任务延迟降多少。
