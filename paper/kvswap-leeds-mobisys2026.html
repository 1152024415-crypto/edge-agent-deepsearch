KVSwap: Disk-aware KV Cache Offloading for Long-Context On-device Inference

深度整理

研究背景与问题

端侧本地跑大模型有隐私、离线、低成本三大好处，但一旦任务变成长上下文——比如会议纪要、视频摘要、长文档分析，常常还要一次处理多条长输入——KV cache 会随上下文长度和 batch 大小线性膨胀，很快把端侧那点内存撑爆。现有的 KV cache offload 方案都是为 GPU→CPU 内存搬运设计的，但端侧的 CPU、GPU、NPU 往往共享同一块统一内存，根本没有独立 CPU 内存可以搬；而端侧的磁盘（闪存）I/O 带宽又很有限，直接套桌面机那套 offload 思路根本跑不动。这就是 KVSwap 要解决的硬约束。

贡献点

贡献是把 KV cache offload 重新设计成「磁盘感知」的端侧专属方案。第一，全 cache 落盘，内存里只留高压缩的元数据用来预测哪些条目接下来要用、该提前预取，把内存占用从「整个 cache」压到「少量元数据」。第二，计算和磁盘访问做硬件感知重叠，趁模型算的时候把下一批 cache 从盘读到内存。第三，读模式按存储设备特性编排，匹配闪存的随机/顺序读性能差异。整体把端侧原本没法用的磁盘，变成能撑长上下文的二级 KV 存储。

实现方法

流程大致是：KV cache 不再全部驻留内存，而是整体写到磁盘；内存里维护一份紧凑的元数据索引，记录每段 cache 何时被用、按预测模型判断哪些段在接下来的生成里会被访问，提前发起磁盘预取。预取和当前 token 的计算重叠——当前层在算的时候，下一层的 cache 已经在从盘往内存搬。读模式按存储设备特性重排，比如把随机小读合并成顺序大读，匹配闪存的顺序带宽优势。这样把磁盘的慢 I/O 藏进计算时间里，让端侧在内存预算极紧的情况下还能跑长上下文。

实验与结果

在一组代表性大模型和多种存储类型上评测。结果：在紧内存预算下，KVSwap 比现有 KV cache offload 方案吞吐更高，同时保持生成质量不退化。摘要没给具体吞吐数字、加速比、设备型号或上下文长度，只给相对定性结论。整体属于系统实测类工作，但定量数据在正文。

对端侧 agent 的意义

这篇对端侧 agent 工程师是直接可用的。端侧 agent 跑长程任务（多轮对话、长文档处理、多工具调用累积上下文）最怕的就是 KV cache 撑爆内存，而现在手机/IoT 的内存就那么大。KVSwap 给的是一条「用磁盘换内存」的路径，而且针对端侧统一内存+闪存带宽有限的现实做了适配，不是桌面方案的硬搬。对做端侧长上下文 agent 的团队来说，这意味着不必砍上下文长度、不必频繁重算前缀，可以把历史 KV 落盘、按需预取，端侧也能撑住长程 agent 工作流。这套机制和前缀缓存、投机解码这些技术是互补的，可以叠用。

局限与未来

第一，磁盘 I/O 再怎么重叠也有上限，当 cache 预取命中率低、或计算时间短于读盘时间时，吞吐会掉，摘要没给最坏场景。第二，预取依赖元数据预测模型，预测不准会触发大量无效读，反而拖累 I/O，预测器的鲁棒性没讨论。第三，闪存寿命有限，KV cache 频繁写盘会磨损，端侧设备这点摘要完全没提，工程上是个隐患。第四，没给绝对吞吐和延迟数字，难以横向对比其他长上下文方案（如滑动窗口、重计算）。未来值得看 KVSwap 在真实端侧 agent 多轮任务下的端到端延迟和闪存磨损实测。
