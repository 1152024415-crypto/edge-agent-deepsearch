TimelyLLM: Time-sensitive LLM Serving System for Physical-I/O Limited Agents

69 2026-06-22 · 学术论文
契合28·厂商8·贡献14·质量14·时效5·开源
Yale University
LLM推理端侧部署机器人agent调度系统延迟优化

深度整理

研究背景与问题

像 GPT-4、Llama3 这种大模型已经能听懂复杂指令，越来越多被用来控制无人机和机器人干活。但问题来了：现在给大模型做推理服务的系统都是按先来先服务（FCFS）批量处理的，这种调度对聊天没问题，对机器人就致命——机器人任务是时间敏感的，晚了 0.5 秒可能就撞墙或错过窗口。FCFS 不会管你这个请求急不急，先排到就先服务，于是机器人的硬实时需求和大模型服务的批处理思维对不上。这篇就是要解决这个错配。

贡献点

核心贡献有两条。第一，提出 segmented generation（分段生成），把机器人任务的 LLM 输出按执行粒度切成段，让生成和执行可以交错，而不是等整段 plan 全吐完机器人才动。第二，设计了一套专门面向多机器人 agent 的调度机制，关键洞察是「plan 生成阶段和执行阶段之间有冗余时间」——机器人在执行前一段时，系统可以提前生成下一段，从而把等待藏进执行时间里。这两点合起来让 serving 系统第一次真正照顾到时间敏感性。

实现方法

实现上把 TimelyLLM 嫁接到一个主流 LLM serving 框架上（摘要没点名是哪个）。流程大致是：机器人请求进来后不是进 FCFS 队列，而是按时间紧迫度排序；生成阶段被切成段，每段生成完就交给执行端，同时调度器判断下一段该在什么时候开始生成才能赶上执行节奏，把生成时间和执行时间重叠起来。调度还要处理多 agent 之间的抢占和优先级，保证急任务不被慢任务堵住。

实验与结果

在一组机器人应用上评测。关键数字两个：time utility（时间效用，反映任务按时完成的程度）提升到 1.97 倍；整体等待时间下降 84%。这两个指标都直击时间敏感性痛点。摘要没给具体硬件、模型规模、机器人平台或绝对延迟数字，也没有和特定基线系统点名对比。

对端侧 agent 的意义

这篇虽然场景是机器人，但对端侧 agent 工程师很有借鉴价值。端侧 agent（手机、可穿戴、IoT 上的 agent）越来越多要管物理 I/O 和时间敏感任务——闹钟、提醒、传感器响应、交互式操作，这些都不是「慢慢排队」能搞定的。TimelyLLM 的分段生成+执行重叠思路可以直接迁移：本地 agent 一边生成计划一边执行上一步，把推理延迟藏进动作时间里。这对资源紧张、又要实时响应的端侧 agent 是一种很有用的调度范式，比单纯堆算力或砍模型更聪明。

局限与未来

第一，实验只给相对指标（1.97x、84%），没给绝对延迟和硬件配置，难以判断在真实机器人负载下能不能达标。第二，分段生成依赖任务可以被自然切成段，对那些必须一次性输出完整 plan 才能执行的任务可能不适用。第三，摘要没提多 agent 之间抢占会不会饿死低优先级任务，调度公平性存疑。第四，实现嫁接在「主流框架」上但没点名，复现门槛不清。未来值得看这套调度放到端侧芯片（手机 SoC）上、面对多 agent 抢同一个本地推理资源时表现如何。
