深度整理

研究背景与问题

Agentic AI 应用把多次模型调用和工具执行串起来跑，给 GPU-CPU 集群的调度出了新难题。难点在于：agent 的推理时长和调用结构往往取决于 prompt 的语义内容——同样一个请求，不同 prompt 拆出来的模型调用次数、工具链路、耗时都不一样。传统调度器是按固定资源画像或先来先服务排的，根本预测不了这种语义驱动的动态调用图，结果就是尾延迟高、SLO 守不住。这篇要解决的就是「怎么给语义驱动的 agentic 负载做低延迟调度」。

贡献点

贡献有三层。第一，引入调度专用的神经网络预测器，输入特征覆盖 prompt、设备、runtime、目标模型四个维度，能预测 agentic 调用的耗时分布，而不是只给一个点估计。第二，把分布式预测暴露给 router 和 scaler，让它们做 tail-aware（尾延迟感知）的决策，而不是只看均值。第三，提供预测器的训练和在线自适应机制，并把这些组件塞进一个 scheduler-agent 框架，作为和现有调度/模型服务基础设施集成公共底座。整体是把「语义感知」第一次系统化塞进集群调度。

实现方法

实现上，预测器是一个神经网络，吃 prompt 特征、设备特征、runtime 特征、目标模型特征，吐出该 agentic 调用耗时的分布预测。这个分布被传给 router（决定请求路由到哪个模型/设备）和 scaler（决定扩缩容），两者都用分布的尾部分位做决策，从而显式压尾延迟。预测器有离线训练流程，也有在线自适应机制应对分布漂移。整套东西包在 scheduler-agent 框架里，对外提供统一接口，能挂在现有调度器和服务框架旁边跑，不需要推倒重来。

实验与结果

评测分两块。一是真实生产部署，规模近 1000 块 GPU 和 100 万 CPU 核；二是受控实验，128 GPU 测试床。负载覆盖三类 agent 工作流：多 agent 代码生成、深度研究、多模态 agentic 流程。结果：相对最强基线调度器，尾延迟最高降 61.5%；在相同 SLO 下，吞吐达到生产调度器的 2 倍。数字很硬，而且是在真实生产规模上测的，不是玩具。

对端侧 agent 的意义

这篇严格说是集群/cloud 侧调度工作，不是手机/IoT 端侧，但对端侧 agent 仍有借鉴价值。端侧 agent 越来越多走「本地小模型 + 云端大模型」混合架构，本地和云之间的请求调度同样面临语义驱动的动态调用图——同一个 agent 任务，不同 prompt 拆出来的本地/云调用比例和顺序都不一样。SwarmX 的「prompt 特征驱动的耗时分布预测」+「尾延迟感知路由」这套思路，可以缩到端云协同调度上：端侧决定哪些步本地跑、哪些甩云端时，用类似预测器估耗时和尾延迟，避免某一步卡死整个 agent 流程。对做端云混合 agent 框架的工程师是直接可借鉴的范式。

局限与未来

第一，方案重，神经网络预测器+在线自适应+scheduler-agent 框架，端侧这种资源紧张的环境直接搬不动，需要轻量化。第二，生产部署规模虽大，但摘要没说是哪家公司的生产环境、什么负载比例，复现和公平对比难度高。第三，尾延迟降 61.5% 是相对 SOTA 调度器，但绝对尾延迟数字没给，看不出实际 SLO 守得怎么样。第四，预测器依赖 prompt 特征，对全新类型 agent 工作流的冷启动表现没讨论。未来值得看这套预测器能不能蒸馏成轻量版、放到端侧做本地/云路由决策。
