深度整理

研究背景与问题

基于大模型的 agent 在各种任务上表现最好，但一到端侧设备上跑，端到端延迟就高得难受。问题不是单个环节慢，而是 prefill（预填）和 decode（逐 token 生成）两个阶段叠加起来慢。再加上 agent 工作流的输入 token 有自己的特殊模式——长上下文、重复模板、工具调用前缀——这些模式如果被忽视，缓存和生成都吃不到红利。作者指出，之前没有人系统地把端侧 agent 的延迟瓶颈拆开看、再一个个消掉，这是这篇要填的坑。

贡献点

两个核心组件，都是纯软件、不碰硬件、不丢精度。第一，针对 agent 输入 token 模式重写 prompt，让前缀缓存（prefix caching）真正吃得上 agent 那些重复出现的结构化前缀，把 prefill 阶段的重复计算压掉。第二，提出 LLM-free 投机解码：用一个不用大模型本身的轻量途径生成候选 token，再由大模型验证，用最小开销换取 decode 阶段的加速。两者合起来覆盖 prefill 和 decode 全流程，并且能无缝塞进现有端侧 agent 框架。作者自称是第一个系统刻画并消除端侧 agent 延迟瓶颈的工作。

实现方法

实现走纯软件路径。Prompt 重写那部分分析 agent 工作流里反复出现的输入模式（比如系统提示、工具描述、固定指令段），把这些段提前排进前缀缓存，新请求进来时尽量复用缓存而不是重新 prefill。LLM-free 投机解码那部分用一个不依赖主大模型的轻量生成器产出候选 token 流，主模型只负责验证接受或拒绝，避免每一步都让大模型从头生成。两个组件衔接上现有 on-device agent 框架，不需要改硬件或量化模型。

实验与结果

在一组代表性 agent 工作负载上测，端到端 1.61 倍加速，精度无损失。摘要明确强调「real systems」（真实系统而非模拟）和「no accuracy loss」，并能无缝集成进现有端侧 agent。没给具体硬件型号、模型规模、prefill 和 decode 各自的分解加速比，只给总加速。

对端侧 agent 的意义

这篇直接冲着端侧 agent 工程师的痛点来。端侧 agent 跑得慢，瓶颈不在模型本身，而在 prefill 和 decode 的全流程叠加；Agent-X 给的是一套不改硬件、不缩模型、不丢精度的纯软件加速方案，而且针对 agent 特有的输入模式定制。对落地来说，这意味着现有端侧 agent 框架可以低改动接入获得 1.61x 提速。特别是「LLM-free 投机解码」这点对端侧很友好——端侧算力本来就紧，用轻量途径生成候选、主模型只做验证，是端侧少有的能负担得起的投机解码形式。

局限与未来

第一，1.61x 是平均加速，没拆开 prefill 和 decode 各贡献多少，也看不出在长上下文、多工具调用等重场景下是否还稳。第二，LLM-free 投机解码的「轻量生成器」具体是什么、命中率多少、拒绝率多高，摘要没说，这决定了实际收益。第三，prompt 重写依赖 agent 输入有稳定前缀模式，对那些 prompt 高度动态、每次都变的 agent 任务帮助有限。第四，纯软件方案的天花板受硬件带宽限制，叠不叠得上 Vec-LUT 这类访存优化没探讨。未来值得看它和端侧超低比特量化、并行 LUT 推理叠起来的复合效果。
