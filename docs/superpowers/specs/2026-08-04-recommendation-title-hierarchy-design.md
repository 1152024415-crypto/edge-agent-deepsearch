# 推荐卡片中文项目名层级设计

## 目标

推荐卡片必须让读者先知道条目叫什么，再了解它做什么。桌面端固定采用「中文项目名 → 一句话介绍 → 关键词 → 推荐理由 → 英文原标题」的信息顺序，完整收录和检索逻辑不变。

## 方案选择

采用独立的 `title_zh` 字段。它是主 agent 阅读来源后为推荐条目编写的短中文名称，不从摘要临时截取，也不覆盖用于来源核对的英文 `title`。

未采用的方案：

- 前端从 `abstract` 自动截取名称：无法区分名称和介绍，会再次出现当前问题。
- 用中文覆盖 `title`、另存英文原题：需要迁移全部历史数据，并削弱现有来源核对契约。

## 页面层级

每张推荐卡片按以下顺序展示：

1. 来源、日期、评分等元信息。
2. `title_zh`：中文项目名，卡片最醒目的文字。
3. `abstract`：一到两句中文介绍，字号和字重低于名称。
4. `tags`：以关键词 chip 展示，并有「关键词」提示。
5. `recommendation_reason`：解释为什么值得优先看。
6. `title`：以小号灰色文字保留英文原标题。

卡片仍是可聚焦的链接，键盘操作和现有点击详情行为不变。筛选后没有推荐时继续使用现有空状态。

## 数据契约

- 自动搜集脚本对所有条目写 `title_zh: ""`，不得自动翻译或从摘要截取。
- `recommendation=推荐` 时，`title_zh` 必填；`recommendation=纳入` 时可为空。
- 非空 `title_zh` 至少包含 2 个中文字符，总长度不超过 40 个字符。
- `title_zh` 不得与 `abstract` 完全相同，不得包含内部占位或流程标记。
- 主 agent 策展推荐时，同时填写 `title_zh` 和 `recommendation_reason`。

## 数据流

`research run JSON` → `agent/research_run.py` 校验和规范化 → `app/storage.py` SQLite 持久化 → `/api/papers` → `app/page.py` 推荐卡片。旧数据库启动时自动增加 `title_zh` 列，原有记录默认空字符串，不丢数据。

## 防回归

- research run 单元测试验证推荐缺少中文名称会失败，纳入条目可留空。
- 存储迁移和 API 测试验证 `title_zh` 不丢失。
- 页面测试锁定名称、介绍、关键词、推荐理由、原标题的 DOM 顺序。
- `gate_release.py` 在真实 `site/index.html` 上复核每条推荐的中文名称，缺失、过长、与摘要相同或含占位词时阻止部署。
- 强入口文档和调研 prompt 同步更新，保证后续每周策展流程主动填写该字段。
